## Blockers to settle first

1. **Open registration — confirmed live in production (2026-09-21).** The
   client has been public-ready since a5ecb09 (2026-09-13): `app.json` sets
   `allowRegistration: true`, and release builds follow it, so iOS 1.2.0 shows
   the Register screen and never showed the "invite-only alpha" note. Checked
   directly against the running infrastructure rather than assumed: the
   `kall-production` CloudFormation stack has `EnablePublicSignup=true`
   (deployed 2026-09-17, `UPDATE_COMPLETE`), and both the API and web ECS
   services are running task definitions with `ALPHA_INVITE_ONLY=false`
   (running count matches desired count on each — not a stale or in-progress
   rollout). `auth.py`'s `_assert_alpha_access` imposes no restriction at all
   when that flag is false, so registration has been open to any Clerk account
   since 2026-09-17 — two days before this submission. Apple's Guideline 3.2
   note ("if intended for specific businesses, organizations or employees...")
   does not apply: sign-up is genuinely open to anyone. Still worth one real
   device registration before recording the video, since infrastructure state
   confirms the gate is open but not that the on-device flow renders cleanly.
2. **Reviewer sign-in — fixed.** Sign-in normally answers with "Confirm this
   device" and mails a code, which is why `app-store-reviewer@skaldandstone.com`
   received codes at 15:49 and 23:45 on Sep 19. The demo account is now exempt
   from device confirmation, so the reviewer signs in with the email address and
   password alone. That exemption is account and production configuration, not
   code in this repository, so nothing here enforces or records it: re-verify it
   on a device that has never signed in before recording the video, and again
   before any future submission, because an exemption that quietly lapses looks
   exactly like the original rejection.
3. **Screenshots — fixed.** The set led with the sign-in screen, which Guideline
   2.3.3 forbids. The sign-in shot is gone from all three sets (iPhone, iPad,
   Play) and the remaining five in-app screens are renumbered 1-5; the capture
   spec no longer photographs the login view. Upload the five current files in
   file-name order when you next edit the listing — the images already in App
   Store Connect are the old set and still lead with sign-in.
4. **In-app purchase has to ship with this submission.** Paid tiers gate real
   features: the free plan's AI allowance is zero, and growth plans, skills
   analysis, resume strategy, and interview prep require Plus. A build that
   cannot sell those plans shows the reviewer upgrade walls with no way through,
   and Apple's own note says in-app purchases should be configured and submitted
   alongside the app. `KALL_MOBILE_PURCHASES_ENABLED` is now set on the shared
   `production` profile and asserted by both store preflights, and EAS production
   already holds both public RevenueCat SDK keys. What remains is store-side, per
   `docs/NATIVE_BILLING.md`: RevenueCat needs an App Store Connect API key to
   import the products and publish an offering; the subscriptions need the
   paid-app banking, tax, and trader information plus a review screenshot each;
   both must be submitted in the same submission as the build; and the production
   stack needs `EnableRevenueCatNative=true` with both Apple product IDs. The
   billing screen offers packages only when the client flag and the API's
   `native_enabled` are both true, so purchasing stays withheld until that
   parameter flips — no new build required to turn it on.
5. **Version drift — fixed.** `app.json` and `package.json` now read 1.2.0,
   matching what App Store Connect holds, and `scripts/version-checks.mjs`
   fails the iOS and Play preflights if the two files disagree or fall below
   the highest version already submitted. The web and API "latest Android
   version" manifests stay at 1.1.6 on purpose: they advertise what is live on
   Play, not what is being built.

### 1. Screen recording

Recorded on a physical iPhone running the current iOS release, starting from app
launch, in this order:

- Launch to sign-in; sign in with the demo credentials below, which need no
  verification code.
- Account registration — creating a brand-new account from the Register screen,
  through email verification and device confirmation, into the workspace. (The
  demo account skips device confirmation; a self-registered account does not, so
  the recording shows the step a real new user sees.)
- Morning Brief — the daily digest that opens on the workspace.
- Opportunities — job discovery across employer ATS boards, with match scoring;
  open one posting to its detail view and the link to the employer's own posting.
- Resume Studio and Tailoring — generating a role-targeted resume revision.
- Application Review — the prepared application, showing that submission requires
  explicit review and approval and that EEO attestations are never auto-filled.
- Applications — status tracking for submitted applications.
- Growth and Achievements — milestone tracking.
- Subscription screen — the Plus and Premium subscriptions with their App Store
  prices, a purchase confirmed through the StoreKit sheet, the feature it
  unlocks now working, and Restore Purchases. Nothing links out to an external
  checkout.
- Workspace → Delete Account — full account deletion, confirmed by typing the
  account email, with the resulting signed-out state.

There is no user-generated content visible to other users anywhere in the app, so
no content reporting or blocking mechanism appears in the recording (see 6).

### 2. Purpose and target audience

Kall is a career operating system for individual job seekers — people running
their own search, typically experienced professionals applying to many roles at
once. The problem it solves is fragmentation: postings live on dozens of separate
employer job boards, each application needs a tailored resume, and status is
tracked by hand across email and spreadsheets. Kall keeps the professional
profile, resume generation, discovery, application preparation, and tracking in
one place, and adds interview preparation and growth milestones. It is
privacy-first by design: profile data is controlled field by field, sensitive
records (EEO, work authorization, reference contacts) are never published or
auto-submitted, and prepared applications always require the user's explicit
approval before anything is sent.

Audience: adult job seekers. No content unsuitable for a 4+ rating.

### 3. Setup and access

Demo account (also entered in App Review Information):

- Email: app-store-reviewer@skaldandstone.com
- Password: [fill in]
- No verification code is needed: this account is exempt from Kall's
  device-confirmation step, so the email address and password are enough on any

Registration is open to anyone — the Register screen on the sign-in view creates
a new account with an email address and verification code. The demo account below
is provided so the reviewer can reach populated data immediately rather than

There is one account type; the demo account has full access with sample data
already loaded — a populated profile, saved resumes, discovered opportunities,
and tracked applications — so every feature is reachable immediately after
sign-in.

To exercise resume upload, any PDF or DOCX resume works (Documents → upload). A
sample file is attached to this reply.

Main features and where to find them: Morning Brief (default tab), Opportunities
(discovery and matching), Documents and Resumes (Resume Studio), Tailoring
(role-targeted revisions), Applications (preparation and tracking), Interview
Prep, Growth and Achievements, Workspace (settings, billing, account deletion).

### 4. External services

- **Clerk** — authentication and session management.
- **Amazon Web Services** — hosting and storage: ECS Fargate, RDS PostgreSQL, S3,
  CloudFront.
- **OpenAI** — the AI service behind resume tailoring, application drafting,
  interview preparation, and profile suggestions. Generated content is always
  presented to the user for review before use.
- **Serper.dev** — a search API over Google results, used to find postings across
  employer applicant-tracking-system job boards.
- **Greenhouse, Lever, Ashby, Workday** — public employer job-board endpoints,
  read only, for discovering and linking to postings on the employer's own site.
- **Google Gmail API (read-only scope) and Microsoft Graph (Mail.Read)** —
  optional, off by default, user-authorized: detects application status emails to
  update tracking. The user connects and disconnects this per account.
- **RevenueCat** — subscription entitlements behind the App Store in-app
  purchases; the app never sees a receipt or payment credential.
- **Stripe** — subscription billing on the Kall website only; never linked from
  or invoked by the iOS app.
- **Sentry** — crash and error reporting.
- **Firebase Cloud Messaging / Expo Notifications** — push notifications for
  reminders and the daily brief.

### 5. Regional differences

The app's features and content are identical in every region — there is no
geographic gating, no region-locked feature, and no region-specific content. The
interface is English only. Job discovery covers employer ATS boards worldwide,
so the postings a given user sees reflect their own search criteria rather than
their location. Subscription pricing, where enabled, follows App Store
storefront pricing.

### 6. Regulated industry and third-party material

Kall does not operate in a regulated industry. It is a personal productivity tool
for job seekers: it is not an employment agency, does not place candidates, does
not charge employers, and makes no hiring or eligibility decisions.

Job postings are publicly available listings retrieved from employers' own
applicant-tracking job boards; Kall displays title, company, location and a
snippet, and links out to the employer's original posting rather than
republishing the listing. No licensed or protected third-party material, and no
third-party credentials, are required to provide the service.

All other content belongs to the account holder — their own resumes, profile,
and application history, uploaded or written by them. There is no user-to-user
visibility in the app: no feed, no messaging, no browsing of other users. Two
features involve outside input, and neither creates content other app users can
see: an optional public career page, which publishes only the fields the user
explicitly selects to a link they choose to share, and testimonials, which the
user solicits from their own references and which remain private to their account
unless they publish them. Because nothing is shared between users inside the app,
there is no content stream requiring reporting or blocking controls.
